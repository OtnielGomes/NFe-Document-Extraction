# README and case study live in this repository, written last

The case study lives in this repository instead of a separate portfolio repository, and the README is written only at the end of the project, after the author confirms its content. Results come from one generated file so no document ever shows numbers the eval did not produce.

## Layout

- `docs/results.md`: generated by the eval script; the single source of every published number. Never edited by hand.
- `docs/case-study.md`: the full write-up, in English.
- `docs/images/`: diagrams and screenshots used by both documents.
- `README.md`: short, recruiter-facing entry point, in English.

## README content

1. One-paragraph pitch with the thesis: the LLM reads the invoice; the code decides whether the reading can be trusted.
2. Link to the live demo.
3. Summarized results table, included from `docs/results.md`.
4. How evaluation and tracing drove the improvements: one short paragraph on the eval → trace → change → eval cycle that chose the production model and prompt (ADR 0008), with numbers taken only from `docs/results.md`.
5. How to run: quality checks (`uv run python scripts/check.py`) and the eval (`scripts/run_eval.py`).
6. Link to the case study.

## Case study content

1. Problem and thesis.
2. Architecture: Section agents, deterministic validator, single Repair attempt, Human review.
3. Results across Extraction approach × Rendition × origin, included from `docs/results.md`.
4. Single-call baseline versus Section agents.
5. Errors caught by the validator, fixed by repair, and reaching Human review; Planted error detection rate.
6. How evaluation and tracing guided the improvements: the first experiment, the failures found in the traces, each change measured as its own experiment against a noise re-run, and the adoption criteria. Numbers come only from `docs/results.md`.
7. Limitations, stated explicitly:
   - Simulated photos are cleaner than Phone photos.
   - The Synthetic set shares one visual layout; the Real set is the layout-generalization evidence.
   - Errors in Unverifiable fields are invisible to the validator.
   - Why there is exactly one Repair attempt.
   - Model snapshots used and the date of the pricing table; a rolling model id has no immutable snapshot.
8. Next steps: fine-tuning a small model and NFS-e.
